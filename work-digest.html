Filtered work digest on named-source retrieval

Zero application code14-day named window

A personal work digest that replaced the morning catch-up, built entirely from instructions over an existing authenticated integration layer. The most useful thing in it is a failure: for several weeks it silently missed an entire source, and the cause was retrieval rather than filtering.

Project scope

Working context arrives across internal team blogs, chat channels and an issue tracker, at a volume that cannot be read daily and with no filter for relevance. That produces one of two failures: skip it and miss something that mattered, or read it and spend the first hour of the day on it.

Neither failure is about volume alone. The specific problem is that relevance is personal. A division reorganization post matters to one person and is noise to another, and no shared feed can make that distinction.

Constraints

  • The output has to be a page that can be opened and scanned, not a chat response that has to be requested.
  • A list of titles with optional descriptions, not prose.
  • The sources are authenticated and internal, reachable only from a local session.
  • The published version must not disclose the author's own goals, profile or objectives.

Approach

Exclusion with named exceptions, not a relevance score

After an early digest surfaced work from unrelated business units, the rule became a single division plus explicitly named carve-outs for the things that break the rule and still matter. A relevance score was rejected deliberately: an exclusion rule with named exceptions is inspectable, and each exception records why it exists.

Separate what must be known from what can be acted on

Three bands, ordered down the page. Critical to know, tagged by type for anything that could reach the support queue. Then awareness only, for organizational and leadership updates. Then the feed, newest first. Neither of the first two bands existed in the original design. Both were added after reading a digest and noticing an absence.

Every row carries a reason

The digest does not just list what happened. Each row says why it is relevant to the reader's current objectives, which is the part a shared feed cannot do. Rows that invite participation go further and name the approach plus something the reader already has to bring, because an entry that requires inventing a new idea does not get used under time pressure.

Implementation

The entire tool is a 64-line command file plus an existing authenticated integration layer. There is no application code. Output is one HTML page republished to a fixed URL so the bookmark never changes. Reading state is per-browser, with pin and done controls, a deliberate fallback chosen after confirming no shared persistence option fitted.

Reuse was designed in from the second day, which produced two artifacts rather than one. The personal instance carries the profile and scope. The public version carries a setup interview that asks each user for their own, plus a neutral template. The separation is enforced by a term scan for profile and objective vocabulary before any commit.

One design detail came from experience with earlier tools of this kind. Asking a user which sources to follow reproduces the original problem, because any source carries noise as well as signal. The setup therefore asks two paired questions per source: what the source is, and what counts as signal from it.

The failure worth reporting

The digest was found to have missed a division reorganization entirely, across several weeks. The cause was retrieval, not filtering. The page was built from the aggregate reader alone, 100 reader posts reaches back only about five days, and sources the reader is not subscribed to never appear at all.

Two things are worth carrying forward. The output gave no signal that a source was missing, so the gap was invisible until someone noticed from outside. And the fix was structural rather than incremental: anything that must not be missed is now pulled by name on a fourteen day window, with comments fetched on any post that asks a question, and the aggregate feed demoted to a supplement.

A second correction followed. A card added two days earlier read the author's own case notes to surface patterns worth reporting. It was removed because this tool runs on an account that must never touch user data, and that source carries it. The command file now carries an explicit prohibition so the card cannot be reintroduced by a later rebuild.

Result

  • In continuous use since the week it was built, with substantive changes still being made two months later.
  • Packaged as an installable plugin with a self-serve setup flow, so a second user does not inherit the first user's profile.
  • Zero code dependencies. Instructions plus an existing integration layer, which means no engineering time to build and none to maintain.

Limits

  • Refresh is manual. A scheduled cloud agent cannot reach a locally authenticated integration, so unattended refresh would need a local scheduled job, which has not been verified.
  • Reading state is per-browser and does not follow the reader to another device.
  • The retrieval layer is internal, so the tool as built does not run outside that environment. The architecture is the transferable part.
