Automated directory and email marketing pipeline for unclaimed events

Classification → Enrichment → Email validation → Email search → Contact research → Directory push → Sync → Outreach

Stack

Browse AIAirtableGoogle Apps ScriptClaude APINeverBouncePexelsPixabayBrilliant DirectoriesDirectoristWordPress REST APIGmail

A pipeline that turns scraped event listings into a published directory, then contacts the organizers behind them. Events arrive in Airtable from a scraper, are sorted by type, and have their description, photo, contact details and social links filled in. Organizer email addresses are checked against a verification service, with repeat searches when one fails. Finished listings publish to the directory unclaimed, and a four-step email sequence invites each organizer to claim theirs.

Project scope

An events directory had to be populated before it had members. The approach was to build the listings first from scraped public sources, publish them unclaimed, then contact each organizer and invite them to claim the listing and choose a plan. Two halves, joined: the directory build, and the email sequence that turns an unclaimed listing into a claimed one.

Eight scheduled jobs carry a record from scraped row to claimed listing, each one responsible for a single stage.

Constraints

No server. Everything runs in Google Apps Script on scheduled triggers, so each stage has to finish inside an execution limit and hold its own state between runs.

The hosted directory platform owns the page templates, so listing structure had to be expressed through its own post types and fields rather than in code.

Model output is plausible by construction. A fabricated contact address is indistinguishable from a real one by inspection. The audience is small event organizers on custom domains, which frequently return inconclusive verification results rather than a clean yes or no.

Enrichment is slow and billed per record. It rewrites the description and photo on every run, at roughly 15 seconds per record, so re-running it to fix one field would overwrite good content and spend credits doing it.

Approach

One job per stage, each reading a database view that holds only the records at that stage. A status field on the record is the state. Adding a stage means adding a status value and a filtered view, not rewriting the pipeline. A stage that fails leaves the record where it is, so the next run picks it up rather than losing it.

Treat the model as a source of candidates, not facts. Anything it supplies that will be acted on externally, which here means a contact address, has to be confirmed by something outside the model before it counts.

Intervals follow cost. A single cheap call can run every few minutes. A slow billed stage runs hourly.

Building the listing

Classification is deliberately cheap and does nothing else: listing type, a filter flag for relevance, and basic field cleanup. Enrichment then writes the description, pulls a photo from a stock image API, and researches the organizer. Contact research is a separate job again, and it writes social links only. It is explicitly barred from writing the contact name or address, because those belong to enrichment and two jobs writing the same field is how records end up inconsistent.

On the directory side the listings are modeled as three separate post types rather than one type with categories. The single type was tried first and abandoned, because categories cannot be access-restricted per membership plan, which the claim and upgrade flow depends on.

The verification gate

Every candidate address is checked against a verification service before it can advance. Only a valid result passes. invalid, disposable, unknown and accept_all are all treated as failures.

Rejecting accept_all was the call that mattered. An accept_all domain acknowledges every address whether the mailbox exists or not, and this audience produces a lot of them. Passing them through would have shown a much higher success rate while reintroducing the exact failure it was built to prevent. Unconfirmed is treated as failed, not as probably fine.

A verification error is different from a verification failure. If the service itself errors, the address is left in place and the record goes to human review rather than being cleared.

The retry ladder

A failed address is cleared rather than kept, and the record enters a search loop with up to three attempts, each broader than the last. Attempt one is whatever enrichment originally found. Attempt two is a wide search on the event name with contact terms. Attempt three targets the named organizer and tries common address patterns on the event domain. Every attempt is re-verified through the same gate.

An attempt counter on the record bounds the loop, and the third failure routes to human review rather than looping forever.

The claim sequence

Listings publish unclaimed, on a free plan, each carrying a claim link. The sequence then sends on days 1, 3, 7 and 14, with a different message each time. Before choosing a greeting it checks whether the address is a generic inbox rather than a person, because addressing an info@ address by first name is worse than not addressing it at all. Messages were composed as drafts first, so the send step could be reviewed before it was armed.

Alternatives I ruled out

  • Resetting records to re-run enrichment. The simplest way to re-check the backlog, and it would have overwritten every existing description and photo. Rejected in favor of a separate validation job.
  • One combined validate-and-search function. Rejected because the two tasks have different speeds and different counter logic, and combining them lets the slow one block the fast one.
  • A single listing post type with categories. Rejected because per-plan access control is applied to post types, not categories, and the claim flow sells access.

Result

Five jobs run automatically. A scraped row becomes a classified, described, illustrated listing with a verified organizer address and social links, without anyone touching it.

The gate and both failure paths were checked against live records before the triggers were enabled. A validation run promoted two confirmed records in 17 seconds with no errors. A search run found and confirmed one record on the first retry; the second returned an inconclusive result, which correctly cleared the address, incremented the counter, and held the record in the retry queue rather than promoting it.

An unverified address can no longer reach a send. That failure is structurally unreachable now rather than avoided by care.
